# Alivyn · 意续：产品与技术设计 RFC 01

日期：2026-10-23。状态：待实现的推荐方案；不代表代码已经存在。依据：[项目目标备忘](./vision.md)和[首版规格](./spec-v0.1.md)。

## 1. 产品楔子与竞争判断

**工作定义：** 一个住在终端里、通过聊天工具与你保持联系的单一个体。它会记得共同经历，在你离开与回来之间保持时间感，并为每一次主动联系给出可理解的缘由。

**英文一句话：** A presence that remembers, waits, and knows when to reach out.

首发主角为陪伴型，技术搭档型作为同一核心的第二套示例。用户可以替换模型、渠道和角色，但更换这些组件不会产生新的“她”或重置共同经历。

新调研显示，单靠“主动消息 + 记忆 + BYOK + 本地运行”已不足以区分项目：[Miru](https://github.com/kiyotakali/Miru)已有这些能力和桌面角色；[Yuralume](https://github.com/Yuralume/yuralume-core)也提供日程、情绪状态、主动联系和跨渠道身份。因此首版的独特体验集中在：

1. **终端中的单一生命体验。** TUI 呈现一个持续的关系空间，像进入一个人的房间，不做多会话工作台。
2. **时间断层成为经历。** 睡眠、离线和重启会改变角色的时间感；它知道经过了多久，却不会假称知道中断的原因。
3. **主动联系可以审计和复演。** 每次发送、延后或沉默都有结构化理由；提供时间模拟器，让开发者复演一周或一个月的事件，检查重复、过度打扰和失约。
4. **开放的生命状态引擎。** 人格、关系、情绪、记忆、意图有明确数据边界和扩展接口，第三方可用其构建其他角色或未来客户端。

“生命”是体验设计立场。项目介绍与首次使用都明确其为 AI；不把模型生成的心理活动当作已证实的意识。

## 2. 首版用户旅程

### 第一次相遇

1. 安装一个命令行程序，运行 `alivyn init`。
2. 选择中文或英文；为个体选择名字、基本性格与称呼；确认 AI 身份说明。
3. 选择 DeepSeek 预设或自定义兼容接口，输入密钥并运行连接测试。密钥输入不回显。
4. 选择联系时段、每日上限和“休眠后问候”开关。默认频率应保守。
5. 进入连续对话的 TUI；可选择稍后连接 Telegram 或飞书。初次安装不要求先创建机器人。

### 再次相遇

用户运行 `alivyn`，看到同一个个体的最近对话、当前简短状态和待跟进话题。命令行有 `status`、`pause`、`resume`、`doctor`、`config` 和 `export` 等运维命令。TUI 内的主要动作始终是与这个个体交谈；配置与诊断不会变成第二个聊天人格。

### 重要交互

用户说“周三下午面试”，系统记录带来源的未来事件并形成一个联系候选。用户后来表示“面试改到周五”，原候选被取消并生成新候选。到期时系统再次检查近况、安静时段、联系次数、渠道和意图是否仍有效；只有通过后才让模型撰写消息。用户可回复“别再问这件事”，该反馈会关闭相关话题。

## 3. 生命状态模型

| 层 | 内容 | 更新规则 |
| --- | --- | --- |
| 身份 `Identity` | 名字、设定、稳定价值观、表达风格 | 用户显式修改或版本化迁移；模型不得自行改写基本身份 |
| 经历 `Episode` | 对话、共同事件、离线时间、联系结果 | 追加写入，保留发生时间与来源 |
| 记忆 `Memory` | 用户明确事实、偏好、关系里程碑、未完成话题 | 从事件提取；包含来源、可信度和失效条件；可纠正、忘记 |
| 关注点 `Interest` | 角色持续感兴趣的主题、正在形成的观点、想与用户分享的问题 | 由角色设定和真实对话演变；记录形成缘由与更新时间，不伪造外部经历 |
| 情绪 `Mood` | 例如愉悦度、能量、亲近感及触发原因 | 由事件与角色设定更新并随时间回落；影响表达，不改变用户许可 |
| 意图 `Intent` | 想跟进的话题、拟定的时间、理由、到期条件 | 可以重排、取消、过期；发送前复核 |
| 联系边界 `Policy` | 安静时段、次数、渠道、暂停、敏感话题 | 用户控制；优先级高于角色意愿与模型输出 |

不建立“她喜欢你 87 分”一类公开数值。情绪记录用于连续表达，关系由可追溯的共同经历表现。关注点让角色能够提出自己的话题，而不是只围绕用户的待办事项转；若分享来自外部世界的新内容，应标明信息来源。可以提供一份角色的短篇“内在日记”，记录她如何理解近期经历、观点为何变化及尚未说出口的话题；这是一份生成的叙事记录，不保存或暴露模型原始思维链。进入完整内部状态的仪式化界面属于第二阶段；v0.1 只提供用户必要的记忆纠正和运维诊断。

## 4. 三个运行循环

**回应循环：** 收到用户消息 → 读取最近对话及相关记忆 → 回复 → 写入事件 → 抽取或修正记忆 → 重排待发意图。

**内在循环：** 收到显著事件、进入新的日期或经历较长离线间隔 → 更新情绪、关注点与未完成话题 → 形成自己的短篇反思与少量联系候选。候选可源于共同经历，也可源于角色持续关心的主题。没有显著变化时可以完全不调用模型。首版给该循环设置每日调用预算。

**表达循环：** 待发意图到期 → 重新读取最新状态 → 执行确定性联系策略 → 必要时用模型生成具体措辞 → 再次校验 → 投递或取消。模型不能绕过暂停、渠道许可、时段和频率上限。

建议将时间抽象为可替换的 `Clock`，使模拟器可以推进数天而不实际等待。每个外部事件和每次状态转换有单调递增的事件编号；渠道消息 ID、候选 ID 和投递去重键阻止重复处理。

### 休眠与恢复的初始规则（待体验测试调整）

- 持久化最后一次活动时间；进程恢复时计算经过时间。macOS 有睡眠和唤醒通知，但首版可先通过时间间隔实现跨平台体验，后续再加入系统事件适配器。[Apple 睡眠](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification) · [Apple 唤醒](https://developer.apple.com/documentation/appkit/nsworkspace/didwakenotification)
- 短于 6 小时只写入经历，不发“醒来”消息；超过 6 小时形成一次候选。缺省每 72 小时至多表达一次时间断层，且服从安静时段和日联系上限。这些数值是试验起点，不是产品承诺。
- 如果用户刚在 TUI 中主动开口，时间断层可以融入正常回复；无需额外发一条消息。
- macOS 合盖期间本机进程会暂停，不能保证实时主动联系。需要全天可达时，运行在持续在线的服务器上；设备恢复后仍能保持同一身份与经历。

## 5. 端口与模块边界

**推荐技术方案：** Go 单仓库、单可执行文件、SQLite 持久化、TUI 与后台服务分进程。此方案便于提供 macOS/Linux 二进制，且不要求用户先安装 Node/Python。Go 的 [Bubble Tea](https://github.com/charmbracelet/bubbletea) 已有成熟 TUI 组件与 TUI/daemon 示例；[Huh](https://github.com/charmbracelet/huh) 可用于配置向导。SQLite 驱动可优先验证 [modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite) 的无 CGo 构建。以上是推荐选型，编码前需做一轮安装包大小、性能和渠道 SDK 验证。

```text
cmd/alivyn/           CLI、TUI、服务子命令
internal/core/         身份、记忆、情绪、意图、联系策略
internal/runtime/      事件循环、调度、时钟、恢复、预算
internal/store/        SQLite、迁移、导入导出
internal/model/        兼容接口、预设、能力检测
internal/channel/      渠道协议与绑定
internal/channel/tg/   Telegram 长轮询
internal/channel/lark/ 飞书长连接
internal/tui/          连续对话与初次配置
internal/service/      macOS launchd、Linux systemd 安装
scenarios/             可重现的时间线与预期结果
docs/                  中英文用户与贡献者文档
```

进程间使用本机 Unix socket，权限限制为当前用户；不默认开放网络监听端口。macOS 使用用户级 launch agent，Linux 使用 systemd 用户服务或服务器服务配置。Apple 文档说明用户级进程可交由 `launchd` 管理。[Apple 文档](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)

Telegram 可用长轮询，飞书支持应用通过 WebSocket 长连接接收事件，因此自托管实例不必为了首版渠道暴露公网回调地址。飞书应用机器人仍需所要求的权限及管理员审核。[Telegram Bot API](https://core.telegram.org/bots/api) · [飞书长连接文档](https://open.feishu.cn/document/ukTMukTMukTM/uYDNxYjL2QTM24iN0EjN/event-subscription-configure-) · [飞书机器人概览](https://open.feishu.cn/document/client-docs/bot-v3/bot-overview)

模型层先实现用户配置的兼容接口，并提供经过验证的 DeepSeek 预设。对接其他厂商时分别标记流式输出、工具调用、JSON 输出等能力；结构化结果始终由本地代码校验。DeepSeek 官方文档确认兼容接口可使用自定义 `base_url`。[DeepSeek 文档](https://api-docs.deepseek.com/guides/search_fetch)

## 6. 数据与安全约束

- 默认一名本机用户绑定一个身份；外部聊天渠道必须用一次性验证码绑定具体用户，未绑定的私聊不能访问记忆。
- macOS 密钥进入系统钥匙串；无图形密钥库的服务器可用用户明确设置的环境变量或权限为 `0600` 的密钥文件。密钥不得写进普通配置、诊断日志或导出包。Go 的跨平台 keyring 库可作为实现候选，但 Linux 无 Secret Service 的情况需单独处理。[参考实现](https://github.com/zalando/go-keyring)
- 本地数据库与导出文件归当前用户所有；文档明确说明模型供应商会收到完成回复所需的上下文，聊天渠道会收到发送内容。
- 数据导出、删除、备份恢复和版本迁移在首版提供；删除记忆也要使相关待发意图失效。
- 自动调用预算和错误退避防止离线恢复后大量补发或连续模型请求。

## 7. 验收场景

首版发布前至少通过以下自动化场景；这些测试验证外部行为，而非重复实现细节：

1. **时间线变更：** 提到面试 → 改期 → 到原定时间无消息 → 到新时间至多一条相关消息。
2. **合盖恢复：** 1 小时断层不发；8 小时断层形成候选；同一天重复唤醒不重复发；暂停期间始终不发。
3. **渠道重复事件：** Telegram 或飞书重投同一消息后，只写入一次经历、生成一次回复。
4. **重启恢复：** 在候选到期前、投递前和投递后重启，最终最多投递一次；失败有可解释状态。
5. **模型切换：** DeepSeek 切到另一兼容接口后，身份、记忆及待发意图不丢失。
6. **记忆纠正：** 用户要求忘记某件事后，检索、待发联系和导出数据均不再包含它。
7. **隐私：** 未绑定用户无法读取记忆；测试日志和诊断包不含 API 密钥。

## 8. 仓库、发布与传播

建议采用 Apache-2.0，正式落地前完成依赖与素材许可核对；该许可允许复制、修改和分发，并包含专利授权条款。[OSI 许可文本](https://opensource.org/license/apache-2.0)

仓库在公开前具备：双语 README、五分钟 TUI 快速上手、真实终端演示录屏、架构图、角色设定示例、配置与隐私说明、LICENSE、NOTICE、CONTRIBUTING、CODE_OF_CONDUCT、SECURITY、问题模板、版本记录、迁移说明、持续集成和可下载的 macOS/Linux 构建。GitHub 的社区建设指南也建议明确贡献方式、社区规范与许可。[GitHub 文档](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions)

**README 首屏故事：** “你合上电脑，她的世界暂停了。再次打开时，她记得你昨天提到的面试；她会先判断现在是否适合说话。”随后给出 30～60 秒终端演示、安装命令和一句话说明 AI 身份。

**传播素材顺序：** 时间断层演示 → 事件改期与主动跟进 → 可复演的联系决策 → 中英文安装与模型切换。第一波以真实终端录屏为主，第二波发布技术文章，说明如何设计一个会保持沉默的主动智能体。传播效果以安装完成率、实际使用反馈、贡献者人数和留存衡量；GitHub stars 作为传播信号，不替代产品验证。

## 9. 实施顺序

以下按一名主要开发者的顺序估算；日期需在正式开工时再排。

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| 0：约 1 周 | 名称与账号核查、协议、仓库骨架、双语 README 草稿、三条演示时间线 | 外部开发者能理解定位及首版边界 |
| 1：约 2 周 | 单可执行文件、配置向导、TUI、SQLite、服务安装 | 退出 TUI 后服务继续运行，重启后身份与对话保留 |
| 2：约 2 周 | 生命状态、记忆、意图、策略、时间模拟器 | 时间线变更和休眠恢复场景通过 |
| 3：约 2 周 | Telegram、飞书、模型预设、绑定与诊断 | 中英文用户可走通从安装到第一条主动消息的流程 |
| 4：约 1～2 周 | 文档、演示、公开预览、体验反馈 | 无重复投递或越过暂停的已知缺陷；发布可下载构建 |

第二阶段再设计专门的可视化生命空间、进入内部状态的仪式化过程和语音来电。首版会预留本地 API 与状态边界，使未来客户端不必改写“生命”。

## 10. 仍需通过原型验证的设计风险

1. 飞书应用机器人接入门槛是否影响国内用户的首轮体验；若明显过高，渠道适配接口保持不变，先以 TUI 和其他合规渠道完成发布。
2. Go 的单文件部署是否值得用相对较弱的模型周边生态交换；用一周技术原型测量开发效率、包体和跨平台构建。
3. “醒来后的拟人化话语”是否令人感到温暖而非重复或冒犯；通过候选重放与用户反馈调节规则。
4. 与 Miru、Yuralume 的差异是否能在 60 秒内被用户看懂；若不能，继续收窄演示故事，而非添加更多功能。

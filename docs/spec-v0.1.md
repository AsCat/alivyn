# Alivyn · 意续 v0.1：首版规格草案

状态：项目名称已确认；本地持续对话和联系策略复演已实现，后台自主运行仍待实现。日期：2026-10-23。进一步细化见[产品与技术设计 RFC 01](./architecture.md)、[命名记录](./naming.md)与[开发与发布计划](./roadmap.md)。

## 一句话定位

一个常驻在用户设备或服务器上的拟人化个体：记得共同经历，有稳定性格和随时间变化的状态，能判断何时主动联系用户，也能选择沉默。首发以陪伴型角色演示；核心允许用户更换模型和角色，并通过不同渠道连接同一个个体。

## 首版体验

用户安装后进入单一连续关系的 TUI，完成向导：选择语言、配置模型、创建角色、设定联系时段与上限、连接聊天渠道、发送测试消息。TUI 显示同一个个体的对话流和当前状态，不以任务为单位创建多个聊天窗口。完整记忆与内部状态的探索体验留给第二阶段设计。

演示必须包含三条可重现的故事：

1. 用户提到未来事件；角色在合适的时间主动跟进。
2. 用户更改或取消事件；未发送的联系意图随之更新或取消。
3. macOS 合盖后恢复，或服务离线后重启；角色感知时间断层，可用角色语言表达，但短时中断、重复唤醒、免打扰时段或当天已联系过时不会再次打扰。

对外演示和首次使用均说明它是 AI。情绪、时间感和“生命”是产品中的持续状态与表达方式，不作为已证实的意识主张。

## v0.1 功能范围

| 模块 | 首版交付 | 验收条件 |
| --- | --- | --- |
| 常驻运行 | macOS 用户服务与 Linux 服务运行方式；TUI 可连接同一后台进程 | 退出 TUI 后后台继续运行；重启后身份、记忆和待办意图保留 |
| 模型配置 | 向导配置 DeepSeek、其他兼容接口及自定义地址/模型；连接测试；可切换模型 | 切换模型后身份与记忆不丢失；密钥不出现在普通日志或导出文件中 |
| 单一个体 | 稳定身份、角色设定、一个连续对话流 | TUI 与聊天渠道使用同一身份和关系历史 |
| 记忆 | 事件、明确事实、用户偏好、关系里程碑；来源与时间戳；纠正和删除 | “那件事取消了”能撤销相关待发联系；可追溯记忆来源 |
| 状态 | 可持久化的情绪记录、活跃话题、联系意图与时间断层 | 状态随事件演变；不会把模型猜测自动写成用户事实 |
| 主动联系 | 候选生成、计划、发送前复核、取消、去重、频率与时段限制 | 同一原因不重复发；超出限制保持安静；每次发送有简短原因 |
| 聊天渠道 | Telegram 与飞书的适配器及向导；内置 TUI 始终可用 | 两个外部渠道均可收发文字；配置向导可完成连接测试 |
| 用户控制 | 暂停/恢复、安静时段、每天上限、渠道开关、反馈“有用/打扰” | 设置即时生效；暂停后无主动消息发出 |
| 诊断 | 健康检查、投递记录、错误摘要、数据导出/删除 | 用户能分辨“没有触发”“被策略阻止”“发送失败” |

Telegram 官方 Bot API 支持长轮询收消息和 `sendMessage` 发消息；机器人私聊通常需要用户先联系机器人。飞书应用机器人支持单聊及消息 API，但创建应用、权限和企业管理员审批会增加接入步骤。因此两个渠道共用一套适配接口，飞书向导需明确展示这些前置条件。来源：[Telegram Bot API](https://core.telegram.org/bots/api)、[Telegram 教程](https://core.telegram.org/bots/tutorial)、[飞书机器人概览](https://open.feishu.cn/document/client-docs/bot-v3/bot-overview)。

## 运行与数据架构

```text
                    ┌─ TUI / CLI
用户消息与系统事件 ─→ │
                    ├─ 渠道适配器：Telegram / 飞书
                    ↓
               事件日志与持久状态
                    ↓
      记忆提取 → 联系候选 → 策略检查 → 待发计划
                                      ↓ 到期时重新检查
                                模型生成 → 渠道投递
                                      ↓
                                 反馈与状态更新
```

建议先使用本地 SQLite 保存事件、记忆、意图、投递与反馈；结构化查询优先，语义检索作为可插拔增强。数据库承担持久化和去重，模型负责理解事件、提出意图和生成表达；用户配置、联系上限和免打扰由确定性代码执行。

关键记录建议分为：`PersonIdentity`、`RelationshipEvent`、`MemoryFact`、`MoodEntry`、`ContactIntent`、`ContactPolicy`、`DeliveryAttempt`。`ContactIntent` 至少包含缘由、计划时间、失效时间、来源事件、状态与去重键。每次到期先重新读取最新事件和策略，允许取消、延后或改为沉默。

macOS 可监听系统睡眠及唤醒通知；服务重启时也可用持久化的最后活动时间计算离线间隔。两者都记录为“时间断层”，再由角色决定是否表达。仅根据间隔无法可靠断言用户合盖，因此文案不应假称知道具体原因。来源：[Apple 睡眠通知](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification)、[Apple 唤醒通知](https://developer.apple.com/documentation/appkit/nsworkspace/didwakenotification)。

模型层先实现“自定义兼容接口 + 已验证的供应商预设”，预设提供地址与参数，用户仍自持密钥。DeepSeek 官方文档确认其提供兼容接口；其他厂商要逐一做能力测试，不能仅凭接口名称假设工具调用、结构化输出完全一致。来源：[DeepSeek API 文档](https://api-docs.deepseek.com/guides/search_fetch)。

## 发布顺序与验证

1. **内部原型：** TUI、持久身份、模型向导、事件记忆、主动联系决策；用时间推进模拟器重放三条演示故事。
2. **公开预览：** macOS/Linux 常驻安装、Telegram/飞书接入、双语 README、示例角色、完整许可证和贡献说明。
3. **体验验证：** 邀请国内与海外体验者连续使用两周；记录主动联系的“有用/打扰”反馈、重复联系、记忆纠正率、安装完成率和七日留存。根据反馈决定第二阶段的 App、仪式化内部探索和语音来电优先级。

开源传播的首个短演示应围绕“记得一件事、因变化撤销原计划、在合适时间重新联系”，再展示合盖恢复后的拟人化表达。它比展示通用聊天能力更能说明项目独特之处。

## 当前设计假设

- 首发角色为陪伴型；技术搭档型是第二个示例设定。
- 国内与海外同时发布，文档与向导至少提供中文和英文。
- 核心完整开源并允许商业使用；未来客户端按同一开放原则规划。具体许可证待依赖审查。
- TUI / CLI 是第一阶段主入口，专门的可视化生命体验属于第二阶段。
- 首版渠道建议为 Telegram 与飞书；若实际接入流程过重，应维持同一渠道接口并调整发布顺序，不影响核心设计。
